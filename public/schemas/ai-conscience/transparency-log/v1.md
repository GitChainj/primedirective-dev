# AI Conscience Transparency Log — v1

A public, append-only, **hash-chained** log of attestation issuance. Format is
**JSONL**: one JSON object per line, in issuance order. The chain lets any
verifier confirm the log has not been reordered or had entries removed, without
trusting the log's host.

## Entry fields

Each line is a JSON object with exactly these fields:

| Field | Type | Meaning |
|---|---|---|
| `seq` | integer ≥ 0 | Monotonic sequence number, starting at 0. |
| `reference` | string | The attestation's public reference (`UPD-YYYY-NNNN`). |
| `signature` | string | The attestation's base64 detached Ed25519 signature. Binds the entry to the exact attestation. |
| `signed_at` | string (date-time) | When the intermediate signed the attestation. |
| `intermediate_fingerprint` | string (16 hex) | Fingerprint of the intermediate key that signed the attestation. |
| `prev_hash` | string (64 hex) | `entry_hash` of the previous line. For `seq` 0 this is 64 zeros. |
| `entry_hash` | string (64 hex) | SHA-256 of the canonical form of this line **minus `entry_hash`**. |

**No adopter name appears in the log** — data minimisation. The `signature`
already binds the entry to a specific attestation, whose public facts live in the
ledger and the attestation document.

## Canonical form for `entry_hash`

`entry_hash = SHA-256( canonical(line without entry_hash) )`, where *canonical*
means: keys sorted alphabetically, serialised as JSON with no whitespace. Note
this canonicalisation drops **only** `entry_hash` — unlike attestation/cert
canonicalisation, the `signature` field is retained because here it is data to be
committed to, not the document's own signature.

## Chain rules

- Line 0: `prev_hash` MUST be `0000…0000` (64 zeros).
- Line *n* (n > 0): `prev_hash` MUST equal line *n−1*'s `entry_hash`.
- Every line: `entry_hash` MUST equal the recomputed hash above.

## Verification

To confirm an attestation is logged, a verifier walks the chain from line 0,
recomputing each `entry_hash` and checking each `prev_hash` link, up to and
including the line whose `reference` **and** `signature` match the attestation.
Presence alone is not enough — the chain from genesis to the matching entry must
be intact. A break before the matching entry fails verification.

## Evolution

Two additive extensions are planned, and both can be built **over** the existing
chain without rewriting or re-signing any v1 entry:

- **Signed checkpoints** — the intermediate (or root) periodically signs a
  `{ seq, entry_hash }` pair, letting a verifier trust a prefix of the log by
  checking one signature instead of walking from genesis.
- **Merkle inclusion proofs** — publishing a Merkle tree over the entries lets a
  verifier confirm a single entry's inclusion with a logarithmic-size proof
  rather than the full chain.

Both are strictly additive: they layer on top of the `entry_hash`/`prev_hash`
chain. **v1 entries are immutable** — once written, an entry's bytes never
change, so any future checkpoint or Merkle layer is computed from the same
canonical entries defined above.
